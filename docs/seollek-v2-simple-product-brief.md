# 설렉 v2 — 심플 개편안

2026-10-22 · 기획 제안 · 구현 전

사용자 지시: 알려진 한계를 개선하고 필수 기능만 담는다. 단 하나의 핵심 기능을 위해 많은 버튼과 화면을 요구하지 않는다. 심플함, 감도 있는 디자인, 편의성과 아이디어를 중심으로 Instagram 활동이 잦은 젊은 여성층을 겨냥한다.

이 문서가 이전 대규모 패치 계획의 제품 구조보다 우선한다. 타깃의 취향·사용 행동을 실제 조사로 검증한 것은 아니며 아래는 검증할 제품 가설이다.

## 1. 제품 한 문장

**“비슷한 사진 중 뭐 올릴지 고민될 때, 친구에게 보내고 함께 고른다.”**

대표 사례는 게시할 사진 후보를 친구에게 보내는 일이다. 사진을 공유·정리하는 범용 앨범이나 새로운 소셜 네트워크로 확장하지 않는다. 친구가 좋은 사진을 고르는 경험과 내가 그 결과로 결정하는 경험이 제품의 중심이다.

## 2. 첫 버전에서 남길 기능

| 남기는 것 | 필요한 이유 |
|---|---|
| 사진 선택·준비·중단 복구 | 시작과 원본 보존 |
| 한 번에 공유하는 요청 링크 | 친구를 데려오는 유일한 기본 경로 |
| 설치 없이 닉네임으로 참여 | 초대받은 친구의 진입 부담 축소 |
| 사진 크게 보기와 별로/글쎄/좋아 | 기존 핵심 판단 방식을 유지하고 다른 선택 모드를 추가하지 않음 |
| 자동 진행·저장, 마지막에 한 번 제출 | 중간 이동과 중복 확인 제거 |
| 친구의 선택과 내 최종 선택·지원 환경의 원본 저장 | 요청을 실제 결정으로 연결 |
| 최소 보관함과 설정 | 다시 열기, 닉네임·데이터 안내·삭제 접근 |

목적 카테고리, 목표 장수 설정, 선택 모드 전환은 첫 버전에 넣지 않는다. 요청에 짧은 부탁을 선택적으로 적는 입력 하나만 둔다. 예: “피드에 올릴 사진 골라줘”. 미입력 시 기본 문구로 보내며 제목 입력을 강제하지 않는다.

## 3. 화면은 네 가지 역할로 통합

다음은 서로 다른 화면 역할의 수이며 운영체제 사진 선택기·공유 시트·권한 팝업을 포함한 클릭 수 약속은 아니다. 오류·복구 안내와 삭제 확인은 필요한 지점에 남긴다.

### A. 홈 — 내 셀렉 보관함

- 상단 작은 설렉 로고와 설정 진입, 아래 사진 중심 요청 카드.
- 유일한 대표 행동은 **사진 골라달라고 하기**. 곧바로 사진 선택기를 연다.
- 내 요청과 친구 요청은 같은 목록에서 소유자·상태로 구분한다. 탭·필터를 처음부터 늘리지 않는다.
- 카드는 “준비 이어하기 / 친구 선택 기다리는 중 / 골라주기 / 결과 보기” 중 현재 행동 하나를 보여준다.
- 친구·마이페이지·앨범 하단 네 탭을 제거한다. 닉네임과 데이터 안내는 설정 패널로 옮긴다.

### B. 보내기 — 사진 준비와 공유를 한곳에서

- 사진 선택 직후 작은 미리보기, 준비 진행률, 선택적 부탁 입력을 보여준다.
- 완료 후 대표 행동은 **친구에게 보내기**. OS 공유 시트 사용, 링크 복사는 대체 행동으로 제공한다.
- 사진 준비 화면에서 요청 생성까지 처리한다. 앨범 이름·요청 제목을 먼저 적는 화면을 없앤다.
- 새 요청은 서버 내부의 독립 컨테이너로 만들고 같은 데이터 계층을 재사용한다. 사용자에게 앨범 개념을 요구하지 않는다.
- 준비 중에는 실패 항목만 재시도한다. 완료 항목을 다시 고르게 하지 않는다.
- 공유 시트를 닫았다고 전송 완료로 단정하지 않는다. “링크 준비됨”과 실제 친구 참여/제출을 구분한다.

### C. 골라주기 — 초대부터 제출까지

- 초대 링크는 요청자·짧은 부탁·사진 수를 확인하고 닉네임을 입력하는 작은 진입 패널로 연결한다. 기존 닉네임이 있으면 재입력하지 않는다.
- 그다음 요청 설명·사진 그리드·시작 버튼을 거치지 않고 첫 미분류 사진을 크게 연다.
- 상단은 순번과 닫기, 중앙은 전체 사진, 하단은 세 분류 버튼. 스와이프는 탐색, 저장 성공 후 자동 이동.
- 세 버튼은 핵심 판단 기능이므로 유지한다. 관리·초대·전체 의견·분류 필터를 이 화면에 섞지 않는다.
- 마지막 분류 후 같은 화면의 패널에 좋아 사진 조합과 **골라주기 완료**를 표시한다. 사진을 누르면 바로 수정하고, 완료 버튼으로 제출한다.
- 별도 제출 전 확인 페이지와 제출 완료 페이지를 없앤다. 성공하면 같은 화면에서 완료와 선택 조합을 표시한다. 세션 유실/저장 실패 시 제출 성공으로 표시하지 않는다.
- 좋아 0장도 가능하다. 마지막 패널에서 “좋아로 고른 사진이 없어요”를 명확하게 보여주고 제출을 막지 않는다.

### D. 결과 — 친구 의견을 보고 내 사진 결정

- 누가 골랐는지와 제출된 조합, 사진별 좋아 수를 사진 중심으로 보여준다. 미제출 초안 반응은 완료된 의견처럼 표시하지 않는다.
- 사진을 누르면 크게 확인한다. 같은 화면에서 최종 사진을 선택한다. 별도 ‘모두의 조합 비교’→‘최종 선택’→‘확정 결과’ 이동을 합친다.
- 대표 행동 **이 사진으로 결정**은 선택 장수와 편집 종료 안내가 있는 패널에서 한 번 확인한다. 기존 확정 후 읽기 전용 규칙을 유지한다.
- 결정 뒤 같은 화면에서 지원 환경에 원본 저장을 제공한다. 웹에서는 지원하지 않는 사진첩 저장 버튼을 노출하지 않는다.
- 후속 요구: iPhone 앱에서는 최종 사진을 **사진 앱의 별도 앨범**에 모아 저장하는 데까지 핵심 흐름에 포함한다. 앨범 이름은 `설렉 · 요청 이름`처럼 자동 지정하고 이름 입력 화면을 추가하지 않는다. 앨범 ID와 사진별 저장 asset ID를 기록해 재시도 시 재사용한다. 필요한 사진 권한은 저장 시 요청한다.
- 최종 결정과 기기 저장의 성공 상태는 분리한다. 저장이 실패해도 최종 결정은 유지하며 결과 화면에서 미완료 항목을 다시 저장한다. 사진 생성은 성공했지만 앨범 추가만 실패한 경우 같은 asset으로 앨범 추가를 재시도한다. 사진 생성 직후 기록 전 종료의 중복 가능성은 실기기에서 검증한다.
- 저장 전 업로드 원본의 크기·체크섬을 확인한다. 여기서 원본은 선택기가 전달한 파일이다. 기존 기기 사진과 asset ID를 연결하지 못하는 경우 저장본이 추가될 수 있으므로 기존 사진의 무복제 재분류를 보장하지 않는다. Safari 웹에서 사진 앱 앨범 자동 생성·분류를 제공한다고 안내하지 않는다.
- 응답이 다 오지 않아도 확인·결정할 수 있다. 대기 중 친구가 있다면 확정 전에 알린다.

## 4. 익숙한 구조를 줄이면서 해결할 알려진 한계

| 한계 | v2 처리 | 범위 제한 |
|---|---|---|
| 앨범/요청 이중 생성 | 사진 먼저 선택, 내부 생성은 자동 | 기존 앨범과 요청 기록·URL은 보존. 기존 공동 앨범은 보관함에서 상세로 접근하는 호환 경로 유지 |
| 새 사진이 모든 제출을 무효화 | 최초 공유 시 사진 묶음을 고정. 공유 후 추가는 기존 사진을 포함한 새 요청으로 보내기 | 이전 요청·제출은 유지. 새 요청은 독립적인 판단 단위이며 반응을 자동 복사하지 않음. 원본 재사용은 접근권한·삭제 수명 검토 후 구현 |
| 초대가 앨범 전체 이력을 공개 | 새 요청은 독립 컨테이너로 격리, 초대 화면에 공개 범위를 명시 | 기존 공동 앨범 링크의 권한은 무단 변경하지 않음. 요청 단위 권한으로 일괄 마이그레이션하지 않음 |
| 앱 종료와 파일 재시도 | 안정된 사진 ID와 완료 기록, 플랫폼별 복구, 오류 뒤 현재 사진 유지 | iCloud 파일 전달 전 대기를 복구 가능 상태로 오인하지 않음 |
| 여러 기기의 상태 차이 | 쓰기 서버 검증, 제출/확정 경쟁 테스트, 필요한 범위만 갱신 | 실시간 통신 도입보다 기존 조회 안정화 우선 |
| 브라우저만 저장된 기록 유실 | 로컬 테스트와 실제 공유 모드를 명확하게 구분 | 로컬 MVP 데이터를 자동 백업된 것으로 안내하지 않음. 계정 연결은 후속 범위 |

‘최초 공유’는 클라이언트 공유 버튼 클릭 추정이 아니라 서버의 링크 활성화 상태로 정의한다. 링크 활성화가 성공해야 공유 시트를 연다. 이후 편집 금지는 서버에서도 검증한다. 미리 고정한 링크를 공유하지 않은 사용자는 다시 공유할 수 있다.

기존 사용자는 기존 요청을 계속 열고 완료할 수 있어야 한다. 새 요청의 간소화된 동선과 기존 공동 앨범 호환 동선을 구분하며, 이전 데이터를 삭제해서 화면 수를 줄이지 않는다.

## 5. 감도 있는 디자인의 기준

- 참고 디자인의 밝은 바탕·부드러운 카드·여백을 가져오되 사진의 색을 왜곡하는 배경 효과는 절제한다.
- 기존 따뜻한 흰색과 차콜, 테라코타 포인트를 유지한다. 타깃이 젊은 여성이라는 이유로 분홍·귀여운 장식을 기본값으로 단정하지 않는다.
- 홈은 커버 사진과 짧은 상태, 고르는 화면은 큰 사진과 세 버튼, 결과는 선택 조합이 주인공이다.
- 큰 브랜드 문구·설명 카드·기술 정보·반복 안내를 기본 화면에서 줄인다. 꼭 필요한 안내는 발생 지점에 짧게 쓴다.
- 눌림·저장·전환은 짧고 섬세하게 표현한다. 장식 때문에 입력을 기다리게 하지 않는다.
- 사진 전체 보기, 한 손 터치, 글자 크기, 대비, VoiceOver, 키보드·안전 영역을 시안 단계부터 확인한다.

## 6. 추가하지 않을 것

독립 친구 관계/검색, 피드, 채팅, AI 추천, 사진 순서 편집, Instagram 자동 게시, 게시물 캡션 생성, 선택 모드 설정, 점수판, 게임화, 신규 소셜 로그인, 유료화 화면을 넣지 않는다. 사진별/전체 텍스트 의견도 새 요청의 기본 동선에서 제외한다. 기존 의견은 호환 화면에서 읽을 수 있게 보존한다.

필요한 아이디어는 기능을 늘리기보다 **사진부터 시작하기, 링크에서 바로 고르기, 마지막 사진에서 자연스럽게 끝내기, 같은 화면에서 결정하기**로 구현한다.

## 7. 실행 순서와 통과 기준

1. 홈·보내기·골라주기·결과 4역할의 클릭 시안을 만든다. 정상 경로 외에도 좋아 0장, 업로드 실패, 중단 복귀, 아직 응답 없음, 접근 불가를 포함한다.
2. 새 요청 하나를 생성→공유→친구 제출→최종 결정까지 연결한다. 기존 네 탭과 중간 확인/완료 화면을 새 동선에서 제거한다.
3. 공유 시 사진 묶음 고정, 독립 초대, 서버 권한과 기존 데이터 호환을 함께 구현한다. 데이터 계약 변경 없이 화면만 먼저 출시하지 않는다.
4. 기존 업로드·저장·동기화 한계를 보완하고 iPhone Safari 및 네이티브에서 검증한다.

시안 수용 기준:

- 요청자는 앨범·제목을 필수 입력하지 않고 사진 선택부터 시작한다.
- 친구는 닉네임 이후 별도 시작/요청 상세 페이지 없이 사진을 고른다.
- 마지막 분류와 완료 사이에 별도 전체 페이지가 추가되지 않는다.
- 화면마다 현재의 주 행동 하나가 식별된다. 안전한 취소·닫기·복구 행동은 제거하지 않는다.
- 사용자에게 설명하지 않고 첫 요청 공유, 친구 제출, 요청자 결과 확인을 수행하게 관찰한다. 기존 경로와 필수 입력/화면 전환/멈춘 지점을 비교한다. 개선 효과는 실제 관찰 후 판정한다.

검증할 기술 계약: 좋아 0장, 세 분류 배타성, 수정자만 제출 무효화, 최종 확정 잠금, 중복 업로드 방지, 등록 응답 유실 시 원본 보존, 비멤버 접근 차단, 새 요청 격리, 기존 URL·이력 보존.

## 8. 작업 상태

사용자의 구현 착수 지시에 따라 첫 앱 코드를 작성했다. 단일 홈·사진부터 요청·공유 시 고정·같은 화면에서 제출/확정·별도 원본 앨범 저장과 재시도 기록을 연결했다. 실제 검증과 출시 차단 항목은 [출시 기록](app-store-release.md)이 기준이다. 서버 SQL은 파일로 작성했으며 적용하지 않았다. 기존 Ruflo 워크플로 `workflow-1792664396097-klzb3g`는 구 계획 등록 상태이므로 실행하지 않고, 새 구현은 `task-1792666857407-x7ie1k`에 기록한다.

설계 참고: [Dribbble Mobile App Design UI UX](https://dribbble.com/services/1781-Mobile-app-design-ui-ux). 앞선 대표 이미지 확인을 사용했으며 추가 사용자 조사나 취향 검증은 수행하지 않았다.
