## 현재까지 된 일

SDK 58로 iPhone Expo Go 접속 경로를 준비했고, 사진 요청·친구 분류·제출·최종 확정·원본 앨범 저장 코드를 구현했다. 사용자는 iPhone에서 기본 기능이 수행된다고 확인했지만, 속도·화면 복잡도·역할 혼동·다량 사진 셀렉에 문제를 보고했다. 이는 모든 기기·권한·오류 복구 검증을 통과했다는 뜻은 아니다.

10월 26일 기준 lint·앱/Edge 타입 검사, 자동 검사 57개(앱 40·SQL/RLS 9·서버 작업 6·출시 도구 2), 웹·iOS Hermes export가 통과한 기록이 있다. 서명된 설치 앱이나 실서버 운영 검증과는 구분한다. 11월 1일에는 앱 lint·타입 검사·40개 테스트를 다시 실행해 **모두 종료 코드 0**으로 확인했다. SQL·Edge·출시 도구와 export는 이번 문서 작업에서 반복 실행하지 않았다. 결과는 [출시 기록](app-store-release.md)에 남긴다.

사용자 [실기기 피드백 8개](iphone-test-feedback-20261026.md)는 보존했다. Claude 답변과 코드의 대조는 진행했으나 계획 문서 저장은 중단된 상태였고, 이번 문서로 정리한다. 아래 개선은 **아직 구현하지 않았다.**

- 원격 참조를 갱신해 확인한 `main`/`origin/main`은 `f17d9fc`(2026-10-10), 현재 작업 브랜치 `codex/refactor-upload-queue`는 `568052d`(2026-10-26)다.

- 교차 검토와 다음 개발은 브랜치 이름뿐 아니라 위 전체 SHA를 기준으로 맞춘다. 이 문서 커밋 뒤에도 앱 구현 기준 SHA는 그대로다.

## 제품 방향과 반영 결정

요청자의 주 흐름은 **사진 준비 → 친구에게 링크 보내기 → 친구 응답 비교 → 최종 사진 모으기**다. 수행자는 **링크 열기 → 분류 → 조합 확인·제출 → 종료**다. 내부의 기존 앨범/간편 모드 구분을 사용자에게 선택하도록 요구하지 않는다. 레거시 URL과 보관 데이터는 유지하며 전체 코드 재작성은 하지 않는다.

온보딩은 시작 버튼 하나를 주 행동으로 두고 약관·개인정보 안내는 읽을 수 있는 작은 링크로 정리한다. 필요한 동의의 의미와 기록은 유지한다. 신고·차단·초대 관리 등은 보조 메뉴로 정리한다.

분류는 좋아/글쎄/별로별 사진 영역과 개수, 미분류 표시를 제공한다. 수행자는 자신의 분류를 보고 수정하고, 요청자는 친구별 필터와 응답을 보며 최종 후보를 고른다. 여러 친구의 의견이 다른 사진을 무작정 하나의 분류로 합치지 않는다. 최종 후보 선택 상태는 영역·필터를 바꿔도 유지하고, 그룹별 전체 선택·해제를 지원한다.

스와이프는 이동, 분류 버튼은 평가로 구분한다. 현재 방향은 왼쪽 다음/오른쪽 이전이고, 사용자가 요청한 방향과 다르다. 이전/다음 버튼을 제공하고 첫 시안에서 방향 규칙을 확인한다. 방향을 합의하지 않은 채 사용자의 보고를 오인으로 종결하지 않는다.

## 원본 처리 개편의 선행 검증

권장안은 **미리보기 중심 공유 + 원본 사진 자산의 기기 내 참조 + 기존 자산을 앨범에 추가**다. 다만 다음 실험을 통과한 뒤 기본 저장 경로로 채택한다.

1. 테스트용 사진에 대해 assetId 획득, 해당 사진의 읽기 권한, 기존 앨범 자산 추가를 확인한다. 전체·제한·거절 권한, iCloud 자산, 앱 재실행, 사진 삭제·편집·권한 변경을 나누어 검사한다. 거절을 전체 권한 강요로 해결하지 않는다.
2. 같은 사진을 두 번 저장해도 새 카메라롤 자산이 생성되지 않고 기존 사진이 앨범에서 열리는지 확인한다. 파일 재생성 경로의 화질 유지와 기존 자산 재사용을 같은 검증으로 취급하지 않는다.
3. 사진 표시 순서는 앱의 확정 ID 순서로 보존한다. Photos 앨범의 표시·정렬은 별도 실기기 확인 항목이며 API 호출 순서만으로 정해진 정렬을 보장하지 않는다.
4. 원본 assetId와 기기 파일 경로는 요청자 기기 내부에만 보관한다. 서버·친구에게는 내부 photoId와 미리보기만 제공한다. 접근 실패 시 재선택·권한 재허용을 안내하고, 파일이 없는 상태를 저장 완료로 표시하지 않는다. 사진이 편집되어 미리보기와 달라진 경우에도 같은 ID만으로 일치한다고 판단하지 않고 재확인·미리보기 갱신 규칙을 둔다.
5. 현재 `photos` 스키마·등록 RPC·원본/미리보기 Storage 검증·안전 검사·삭제 작업을 함께 점검한다. 새 미리보기 공유 방식과 기존 원본 보관 요청이 공존하도록 호환 변경을 설계하고, 기존 요청의 원본을 일괄 삭제하지 않는다. 실제 보관 대상이 달라지면 정책·앱 안내도 맞추되 확정 후 서버 30일 보관·직접 삭제 가능 원칙을 유지한다.
6. assetId가 없는 사진은 제공된 파일을 이용하는 기존 검증 가능한 경로를 유지하되, 복사본 생성 여부를 안내한다. 새 ID 경로를 입증하지 못하면 기존 저장을 망가뜨리는 전면 전환을 하지 않는다. 별도 원본 클라우드 백업 상품은 이번 범위에서 제외한다.

근거: Expo 문서는 assetId가 `null`일 수 있고 제한 접근일 때도 없을 수 있음을 명시한다. 기존 자산 ID를 앨범에 추가하는 API는 제공하지만, 모든 기기·권한·소요 시간을 보장하지 않는다. [ImagePicker](https://docs.expo.dev/versions/v58.0.0/sdk/imagepicker/#imagepickerasset), [MediaLibrary](https://docs.expo.dev/versions/v58.0.0/sdk/media-library-legacy/#medialibraryaddassetstoalbumasyncassets-album-copy)

## 이번 스프린트에서 보류할 항목

- **확정 후 추가 선정:** 필요성은 수용한다. 다만 최초 확정을 다시 여는 대신 후속 선정 묶음을 추가하는 안을 다음 사양으로 검토한다. 최초 친구 제출·확정 ID·저장 완료 기록을 덮어쓰지 않고, 추가 선정이 30일 만료를 자동 연장하지 않도록 한다. 구체 API·중복 저장·순서는 기록 읽기와 저장 경로 검증 후 확정한다.
- **자동 원본 백업·기기 간 복구:** 원본을 사전에 보관하지 않은 상태의 복구는 약속하지 않는다. 필요한 경우 별도 동의·보관 정책·용량 설계를 포함한 후속 작업으로 분리한다.
- **신고/차단 삭제:** 기능 자체는 유지하고 낮은 빈도에 맞게 노출만 줄인다. [Apple 1.2](https://developer.apple.com/app-store/review/guidelines/#user-generated-content)의 요구와 실제 공유 흐름을 기준으로 검토한다.
- **main 즉시 병합·스토어 제출·새 UI 전면 재작성:** 이번 문서 작성이나 기준선 커밋과 별개다. 현재 Apple 유료 가입 선행 없이 가능한 Expo Go·테스트 서버 검증을 우선한다.
