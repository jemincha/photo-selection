# 사진 준비 속도와 중단 복원 — 2026-10-10

## 발견한 문제와 변경

기존 웹 사진 선택기는 모든 원본을 동시에 이미지로 열어 크기를 읽었다. 대량 선택 시 원본 디코딩이 겹치고, 선택 목록은 화면 상태에만 남아 새로고침하면 사라졌다. iPhone의 실제 새로고침 원인은 로그 없이 확정하지 않았다.

웹에서는 브라우저가 전달한 File을 바로 받아 파일 이름 목록부터 IndexedDB에 기록한다. 파일을 한 장씩 임시 보관한 뒤 원본 검증, 미리보기 생성, 등록을 순차 처리한다. 미리보기는 긴 변 720px의 작은 캔버스에서 만들며, 대기 목록은 원본 이미지를 표시하지 않는다. 원본 SHA-256 검증은 1MB 단위로 나누고 화면이 응답할 시간을 준다. 원본 파일의 형식과 바이너리는 변경하지 않는다.

같은 주소로 다시 열면 목록을 복원한다. 완료한 사진은 건너뛰고 남은 사진만 이어서 처리한다. 임시 파일 보관 전에 중단된 항목은 이름이 남으며 같은 사진을 다시 선택하면 기존 ID에 연결한다. 등록 직후 중단돼도 같은 ID를 확인해 중복 등록을 피한다.

## 범위와 제한

- 파일 선택기에서 앱으로 File이 전달되기 전의 iCloud 다운로드는 앱이 제어하거나 임시 보관할 수 없다. 사진 보관함 대기 시간에는 직접 고르는 시간도 포함된다.
- 복원은 같은 브라우저와 같은 주소(프로토콜·호스트·포트)의 저장소를 사용한다. IP 변경, 비공개 모드, 저장소 삭제·부족 시 복원을 보장하지 않는다.
- HEIC 미리보기는 Safari의 형식 지원에 따라 달라진다. 실패한 원본은 재시도할 수 있다.
- 이번 변경은 Safari를 포함한 웹 경로다. 네이티브 업로드는 별도 경로이며, 여러 탭의 동시 처리 잠금은 구현하지 않았다.
- Supabase 실제 연결과 iPhone 실물의 메모리 사용량·iCloud 다운로드 속도는 아직 검증하지 않았다.

## 검증

- 타입 검사와 Expo 린트 통과, 자동 테스트 16개 통과.
- 자동 테스트: 20개 파일 중단 복원, 순서·ID 유지, 완료 항목 건너뛰기, 실패 항목 재시도, 빠른 중복 실행 방지, 저장 실패, 정확한 SHA-256 확인.
- PC 브라우저: 4032×3024 JPEG 20장, 장당 약 8.1MB를 순차 처리해 20/20 완료. 완료 후 실제 새로고침으로 목록과 720px 미리보기 20개 복원 확인. 처리 중 강제 종료는 자동 테스트로 검증했고 PC 브라우저의 강제 종료 재현은 하지 않았다.
- 기존 방식 대비 속도 향상률과 iPhone 처리 시간은 측정하지 않았다.

## iPhone 재검증

현재 실행 중인 앱을 같은 주소에서 새로고침한 뒤 iCloud 사진 18~20장을 선택한다. 파일 전달 후 목록이 먼저 나타나고 완료 수가 증가하는지 확인한다. 느리거나 실패하면 **처리 시간 · 사진 준비 도움말**에서 대기 시간, 원본 검증, 미리보기, 보관 단계와 오류를 확인한다. 중단되면 같은 요청의 사진 추가 화면을 열고 **남은 사진 이어서 준비하기** 또는 **중단된 사진 다시 선택**을 사용한다. 사진 개수가 중복 증가하지 않는지도 확인한다.
