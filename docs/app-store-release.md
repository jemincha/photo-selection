# 설렉 v2 · App Store 출시 기록

## 최신 상태 · 2026-10-26 · Expo Go SDK 58 대응

사용자 iPhone의 Expo Go가 SDK 58을 요구하고 기존 프로젝트 SDK 57을 거절하는 로그를 확인해 Expo 58.0.19·Router 58.0.26·React Native 0.88.0·React 19.3.0과 호환 Expo 모듈로 갱신했다. 파일 저장은 SDK 58에서 비동기로 바뀐 `File.write()` 대신 기존 완료 순서를 유지하는 `writeSync()`로 변경했다. URL 검사는 삭제된 query-string 의존 대신 현재 Router의 실제 파서를 실행한다.

`scripts/verify.ps1 -SkipWebExport` 통과: 앱 40·SQL/RLS 9·서버 작업 6·출시 도구 2, 합계 **57개**, lint·앱/Edge 타입 검사 통과. 별도 웹 export와 iOS Hermes export도 통과했다. iOS 출력은 `mobile/.expo/sdk58-ios`의 3.6MB 번들이며 서명된 설치파일이 아니다. 첫 샌드박스 실행은 임시 HBC 파일 쓰기 권한으로 실패했고 정상 권한으로 같은 검증을 재실행해 성공했다.

Expo의 번들 내 호환표와 `npm ls --depth=0`으로 버전 정합성을 확인했다. 원격 well-known versions endpoint는 사용할 수 없어 로컬 맵을 사용했으며 Expo Doctor 실행 결과로 기록하지 않는다. npm 감사 high 5개와 출시 전 재검토 항목은 [보안 기록](../release/dependency-security.ko.md)에 남겼다. 실제 서버·사진 저장·서명·심사 증거는 계속 pending이다.

사용자는 기존 개발 서버를 Ctrl+C로 종료한 뒤 `mobile`에서 `npx expo start --go --clear`를 실행하고 새 QR로 접속한다. 기존 로그인·사진 데이터·환경 파일은 초기화하지 않았다. 설치 복구 사본은 커밋에서 제외된 `mobile/.expo/sdk58-install-backup`에 보관했다. [iPhone 실행 안내](iphone-expo-go-guide.md)

## 이전 검증 · 2026-10-23

2026-10-23 · 핵심 흐름과 출시 안전 기능 구현·로컬 검증. 실제 서버·iPhone 검증 전이며 심사 제출 가능한 상태가 아니다.

### 구현 범위 · 2026-10-23

사용자가 선택한 정책은 **최종 확정 후 30일 보관, 그 전에도 직접 삭제 가능**이다. 운영자와 공개 문의 이메일은 아직 미정이다.

계정 없이 준비한 범위:

- 사진/결과/준비 화면의 ••• 관리 메뉴: 신고, 참여자 차단, 초대 링크 교체·중지·재개, 셀렉 삭제.
- 설정의 약관·사진 보관·도움·계정 삭제 화면. 삭제는 서버 접수→기기 정리→로그아웃 순서이며 중단 후 기존 대기 작업을 재사용한다. 삭제 확인 전 기기 정보부터 지우지 않는다.
- private 신고·차단·삭제 작업·동의 기록, 삭제/차단/만료 계정의 RLS 차단, 30일 만료 정리와 재시도용 서버 함수.
- 공유 전 OpenAI Moderation 검사. 서버가 선택한 미리보기와 부탁 문구만 보내며, 정확한 사진 집합과 제목에 승인을 묶는다. 동의·호출 제한을 적용하고 키 누락·검사 오류·거절 시 공유를 막는다. **별도 실제 API 키와 탐지 품질 검증이 필요하다.**
- 사용자용 `app-actions`의 플랫폼 JWT 검증을 켜고, 유지보수용 secret 인증은 별도 `maintenance` 함수로 분리했다. 하나의 삭제 작업이 실패해도 같은 배치의 다른 작업은 처리한다.
- 기존 자유 댓글은 읽기만 유지하고 새 작성 권한은 닫았다. 새 v2 흐름은 사진 분류와 제출만 제공한다.
- 네이티브 임시 업로드는 완료 기록 뒤 staging 사본을 정리한다. 손상된 manifest는 자동 재생성하지 않고 오류를 알리며, 손상된 기록 때문에 계정 삭제까지 막히지 않게 했다.
- 앱 아이콘·favicon, 스토어 설명·심사 노트·스크린샷 촬영 계획·App Privacy 자료 초안, 로그인 없는 공개 정책/지원 HTML 템플릿과 실제 운영값 검증 생성기.
- `scripts/verify.ps1`로 앱 lint·타입·테스트, Edge 타입·실패 주입, 실제 PostgreSQL SQL/RLS, 웹 export를 한 번에 검사한다. `scripts/release-check.cjs`는 계정·실기기·운영 증거가 빠진 현재 상태에서 실패한다.

새 안전 migration은 `supabase/migrations/20261022131932_release_safety.sql`이며 앞선 세 파일 다음에 적용한다. 네 파일 모두 PGlite PostgreSQL에서 실행했다. 이는 Supabase Auth/Storage HTTP, 스케줄러, 다중 DB 연결의 경쟁 검증을 대신하지 않는다. `supabase/operations/enable-maintenance.sql`은 테스트 서버를 연결한 뒤 별도로 적용할 스케줄 등록 파일이며 아직 실행하지 않았다.

현재 로컬 자동 검사 **57개 통과**: 앱 40개, SQL/RLS 9개, 서버 작업 6개, 출시 도구 2개. 앱·Edge 타입 검사와 웹 export도 통과했다. iOS Hermes 번들은 `.expo/release-ios-rc-20261023`에 생성했으며 설치 가능한 서명 빌드나 실제 Photos 저장 성공을 뜻하지 않는다.

출시 인수인계는 [운영·연결 절차](../release/operations.ko.md), [스토어 등록 초안](../release/store-listing.ko.md), [실제 검증 대기 목록](../release/review-evidence.json)에 정리했다. 아래 2026-10-22 기록은 초기 구현 이력이며 최신 상태는 이 절과 대기 목록을 우선한다.

## 이번 구현

- 메인 하단 네 탭을 제거하고 사진 요청 보관함과 설정 패널로 통합했다. 기존 앨범/요청 URL은 남겼다.
- 사진 선택기를 최초 탭에서 열고, 선택이 끝나면 별도 앨범 이름·제목 입력 없이 독립 요청을 만든다. 웹은 기존 영속 큐, 네이티브는 문서 폴더의 임시 원본과 작업 목록으로 복구한다.
- 사진 준비 후 선택적 부탁과 공유를 제공한다. 공유 시트 닫힘을 실제 전달/제출 성공으로 취급하지 않는다. 웹은 Safari 사용자 동작 제한 때문에 서버의 링크 준비 후 공유 버튼을 다시 누르는 경로를 사용한다.
- 새 요청에 `simple`과 `published_at`을 도입했다. 링크 활성화 이후 사진 추가를 클라이언트와 SQL에서 차단한다. 기존 공동 앨범은 호환 경로를 유지한다.
- 마지막 분류에서 같은 화면의 조합 패널로 제출한다. 좋아 0장 제출과 선택 수정 시 본인 제출 무효화 정책을 유지한다.
- 최종 후보와 확정 결과를 한 화면에 통합했다. 좋아 수에는 제출된 스냅샷만 반영한다.
- iPhone 원본 저장은 파일 크기/체크섬 확인→Photos asset 생성→별도 앨범 추가→완료 기록 순서다. 앨범 추가만 실패하면 asset ID를 재사용한다. 최종 결정과 기기 저장 결과를 분리한다.
- production 빌드는 서버·HTTPS 웹 참여 주소·iOS 앱 식별자가 없으면 구성 단계에서 실패한다. 불필요한 Apple 로그인 entitlement/plugin 설정을 제거했다.

## 외부 환경

사용자 확인: Apple Developer 유료 계정과 Supabase 프로젝트가 모두 아직 없다. `.env`도 없으며 로컬 모드로 검증한다. 원격 DB 변경·클라우드 빌드·TestFlight 업로드·심사 제출을 수행하지 않았다.

## 실제 검증 기록

- 2026-10-23: `http://127.0.0.1:8788`의 웹 export에서 약관 이동·복귀→새 로컬 닉네임→가상 JPEG 두 장→초대 중지/새 링크 재개→테스트 친구 좋아/글쎄→조합 제출→요청자 복귀→친구 픽→한 장 확정을 확인했다. 로컬 신고 접수 안내도 확인했다. 신고는 운영자에게 전송되지 않았다.
- 계정 삭제는 입력 전 비활성·‘삭제’ 입력 후 활성·취소를 확인했다. 브라우저에서 영구 삭제를 실행하지 않았고, 실제 삭제·실패·재시도는 격리된 자동 검사로 확인했다.
- 홈·결과의 320px, 신고 패널의 390px에서 가로 넘침 없음. 캡처: `docs/screenshots/v2-result-20261023.jpg`, `v2-management-20261023.jpg`. 실기기 화면이나 App Store 제출용 최종 스크린샷은 아니다.
- 미리보기 개발 서버의 로컬 소켓 연결이 제한돼, 외부 배포 없이 loopback 전용 정적 서버로 웹 export를 확인했다. 사용자 데이터가 있던 이전 origin은 초기화하지 않았다.
- 서버의 계정 삭제 작업은 원래 사진 요청 ID 목록을 보존해 DB 정리 뒤 Auth 삭제가 실패해도 Storage 경로를 재시도할 수 있다. 이 경우를 SQL 검사에 포함했다.
- 차단 후에도 각 요청자는 본인이 올린 사진을 관리·저장·삭제할 수 있도록 예외를 두었다. 상대방 요청·사진 접근은 막는다. 이 경우를 로컬·SQL 검사에서 확인했다.
- 이용 제한 계정 화면에도 명시적 삭제 확인 입력과 계정 삭제 경로를 제공한다. 제한된 계정이 삭제를 시작하고 제한 기록까지 정리되는 경우를 SQL 검사에 포함했다.
- 보안 패치 뒤 한국어·비정상 percent 인코딩이 함께 들어간 URL로 최신 웹 번들을 열어 기존 셀렉이 정상 표시되고 콘솔 오류가 없음을 확인했다. `scripts/preview-web.py`의 8789 포트에서는 `/terms` 직접 접근도 확인했다.
- Expo 57.0.31·Router 57.0.29 호환 패치와 공식 URL 디코더 보안 수정 적용. SDK 변경 뒤 Metro의 이전 파일 캐시가 EINVAL을 일으켜 캐시를 초기화한 뒤 iOS Hermes export를 다시 통과했다. 취약점 감사에는 공식 수정판 없는 빌드 도구 두 종류에서 전파된 고위험 18개 경로 경고가 남는다. [상세 보안 기록](../release/dependency-security.ko.md)을 참고하며 dependencies 출시 조건은 pending이다.

- 최종 검사: lint·타입 검사, 자동 테스트 **29개 통과·0개 실패**, 웹 export 통과. iOS Hermes JavaScript 번들도 `.expo/v2-ios-native-check-20261022`에 생성했다. 이 결과는 서명된 설치 가능 앱이나 실기기 성공을 뜻하지 않는다.
- iOS 검사의 기존 `dist-ios` 정리와 샌드박스 임시 HBC 쓰기에서 권한 오류가 있었다. 기존 폴더를 삭제하지 않고 새 폴더와 로컬 컴파일러 실행 권한으로 재검증해 통과했다.
- 앨범 저장 테스트는 Photos API를 대체한 상태 전이/실패 주입 테스트다. 실제 사진 앱 저장 성공을 뜻하지 않는다.
- 브라우저 검증은 별도 로컬 origin을 사용해 기존 데이터를 초기화하지 않는다. 예시 파일은 `.upload-fixtures/`의 가상 이미지다.
- `http://localhost:8083`에서 닉네임→최초 버튼의 사진 선택기→가상 JPEG 2장→요청 자동 생성→테스트 친구 분류(좋아/글쎄)→마지막 사진의 제출 패널→제출 완료→요청자로 복귀→친구 픽 확인→최종 후보 1장 확정을 확인했다. 390px 폭에서 가로 넘침 없음, 웹 미지원 저장 버튼 없음도 확인했다. 실제 기기 간 공유 검증은 아니다.
- 기존 `localhost:8082` 저장소를 열며 일부 미리보기 유실이 전체 목록 조회를 막는 문제를 발견해, 사진별 `unavailable` 표시와 대체 미리보기를 추가했다. 데이터 초기화로 해결하지 않았다.
- CLI 안내는 [HTML](supabase-cli-guide.html)과 [Markdown](supabase-cli-guide.md)으로 작성했다. 여덟 항목, 설명 펼치기와 320px 가로 넘침 없음, 로컬 문서 링크 경로를 확인했다. 외부 링크는 공식 문서·소스 링크를 사용한다.
